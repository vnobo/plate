# i18n guide (Angular build-time localization)

The UI ships as two localized builds of the same application:

| Locale | Role | URL | Catalog |
| --- | --- | --- | --- |
| `zh-Hans` | source locale, default | `/` | strings live in templates and `$localize` |
| `en-US` | translation | `/en-US/` | `src/locale/messages.en-US.xlf` |

Translation is resolved **at build time** by `@angular/localize`. There is no runtime
catalog and no translation library: switching language reloads the page in the other build.
`ng build` alone is not localized; `ng build --configuration production,i18n` is.

## Commands

```bash
pnpm i18n:extract     # write the source catalog to src/locale/.generated/messages.xlf
pnpm build:localized  # production build of both locales (alias: pnpm build:i18n)
pnpm test             # unit tests (source locale only)
```

`src/locale/.generated/` and `src/locale/messages.xlf` are gitignored. Only translation
catalogs (`messages.<locale>.xlf`) are tracked.

## Where the pieces live

- `src/app/core/i18n/locale.ts` — locale ids, subPaths, cookie/storage keys, URL helpers,
  `Accept-Language` and cookie parsing. Framework-free so `src/server.ts` reuses it.
- `src/app/core/i18n/locale.service.ts` — active locale (`<html lang>` of the served build),
  persistence (cookie + storage) and `switch()` (full reload, keeps path/query/hash).
- `src/app/layout/locale-switcher.ts` — the shared language menu
  (`variant="nav"` inside the admin navbar, `variant="ghost"` on auth/error/marketing pages).
- `angular.json` — `i18n.sourceLocale`, `i18n.locales`, the `i18n` build configuration,
  `i18nMissingTranslation: "error"` and `security.allowedHosts`.
- `src/server.ts` — static caching, `GET /` locale negotiation, Angular app engine.

## Marking user-facing copy

Every string a user can see must be marked. Template text:

```html
<h2 i18n="@@loginTitle">登录您的账户</h2>
<input i18n-placeholder="@@loginUsernamePlaceholder" placeholder="手机号或邮箱" />
<a i18n-title="@@loginForgotComingSoon" title="即将推出">忘记密码？</a>
<nav i18n-aria-label="@@galleryNavLabel" aria-label="展板导航"></nav>
```

Interpolations and ICU stay in the message:

```html
<span i18n="@@headerUnreadCount"
  >{unreadCount(), plural, =0 {无未读} other {# 条未读}}</span
>
```

TypeScript strings use `$localize`:

```ts
title: $localize`:@@route.platform.users:用户管理`,
this._message.error($localize`:@@login.badCredentials:用户名或密码错误，请重试`);
```

Prefer a `switch`/function over a module-level constant when the value is only needed at
render time; it keeps `$localize` calls out of import side effects.

### Message ids

- New ids use `@@<area>.<feature>.<key>` (`route.platform.users`, `login.missingToken`).
- Ids that already exist are **frozen**: renaming an id throws away its translation.
- Ids are explicit on purpose. When the source text changes, review the matching target in
  `messages.en-US.xlf` in the same change; extraction cannot flag that drift.

### Do not translate

Brand names, locale endonyms (`简体中文`, `English`), log/exception codes, API fields,
CSS class names and test fixtures that intentionally contain Chinese data.

### ICU and placeholders

- Chinese usually only needs `=0`/`other`; English needs `one`/`other`. Keep the placeholder
  name (`VAR_PLURAL`) unchanged in the target.
- Never drop `${...}` interpolations or `<x id="..." />` tags from a target.
- Keep leading/trailing spaces only when the source has them.

## Workflow for a new string

1. Add the string with an `i18n`/`i18n-*` attribute or `$localize`, using a new id.
2. `pnpm i18n:extract` and check the new unit in `src/locale/.generated/messages.xlf`.
3. Add a `<target>` for the id in `src/locale/messages.en-US.xlf` (English).
4. `pnpm build:localized` — a missing target fails the build (`i18nMissingTranslation: "error"`).
5. `pnpm test`.
6. Spot-check both builds: `/` is Chinese, `/en-US/` is English, `<html lang>` and
   `<base href>` match.

## Runtime switching and deployment

- A switch writes `plate-lang` (cookie + storage) and navigates to the other subPath with
  `localeService.switch()`. The page reloads; in-flight form state is lost by design.
- The Express server redirects `GET /` to `/en-US/` when the cookie or `Accept-Language`
  prefers English. Any other path is served by the locale embedded in the URL.
- `security.allowedHosts` in `angular.json` currently allows `localhost` and `127.0.0.1`.
  Set the deployment host with the framework environment variable
  `NG_ALLOWED_HOSTS="plate.example.com,*.example.com"` (it overrides the build value), and
  `NG_TRUST_PROXY_HEADERS="x-forwarded-host"` when running behind a reverse proxy.
  Without an allowed host the SSR engine answers `400 Bad Request`.
- `PORT` selects the listen port (default `4000`).
- Hashed build output is served `public, max-age=31536000, immutable`; HTML shells,
  `ngsw.json`, the web manifest and service workers are sent `Cache-Control: no-cache`.
- One server serves both locales: `server/angular-app-engine-manifest.mjs` lists
  `supportedLocales` and routes `/en-US/**` to the en-US server entry point.

## Locale-aware formatting

- `LOCALE_ID` is provided by the localized build; do not override it in `app.config.ts`.
  Source-locale dev builds report `en-US`, so keep `DatePipe` formats locale-neutral
  (`yyyy-MM-dd HH:mm`) or derive the locale from `LOCALE_ID` as `data-table-demo.ts` does.
- `src/app/plugins/dayjs.locale.ts` maps `zh-Hans → zh-cn` and `en-US → en` from the
  served `<html lang>`; never call `dayjs.locale('zh-cn')` directly.
- Use ICU for counts instead of concatenating numbers and unit words.

## Known gaps

- `index.html` (`<title>`, meta, boot splash, `noscript`) and `manifest.webmanifest` are not
  localized; `manifest.lang`/per-locale manifests are still open.
- Route `data` is not translated (only `title` is); do not put user-facing copy in `data`.
- Dynamic content (menu names, dictionary labels, backend messages) is out of scope; see
  `docs/i18n-review.md`.
- The remaining hardcoded English UI is tracked as migration debt in the same review.
